# PAD — Markdown-PAD記法の起草メモ(第42ラウンド)

PAD(Problem Analysis Diagram・JIS X 0128)をMarkdownの箇条書きで書く記法の、依頼者原案の
捕獲と検討メモ。本格的なデッサンは進め方③(PAD/Okute)の番で行うが、
「頭の中のデッサンが新鮮なうちに文書へ」の原則で先に記録する。

-------------------------------------------------------------------------------
## 依頼者原案(第42ラウンド): 7つの構造で足りる
-------------------------------------------------------------------------------

「①連接②選択③反復④フォーク⑤ジョイン⑥定義(関数呼び出し)⑦Breakが揃っていれば大丈夫」

```markdown
- 連接1
- 連接2
- 連接3
```

```markdown
- s. 選択1
  - 選択肢1
  - 選択肢2
```

```markdown
- w. 繰り返し前判定
  - 連接
```

```markdown
- l. 繰り返し後判定
  - 連接
```

```markdown
+ f. フォーク元
  - f. フォーク先1
  - f. フォーク先2
```

```markdown
- j. ジョイン元1
- j. ジョイン元2
  + j. ジョイン先
```

```markdown
* 定義
```

```markdown
- b. Break
```

- フォーク/ジョインは最新のPAD系規格の拡張(並行処理の表現)に倣う(依頼者)。
- 実例第1号: MederuU器デッサンの「中心ワークフロー」図をこの記法で書き直した
  (`00-dessin.md`参照。ASCII罫線の図はインデント崩れするため全廃)。

-------------------------------------------------------------------------------
## AIの所感(第42ラウンド)
-------------------------------------------------------------------------------

- **接頭トークン(s./w./l./f./j./b.)+`.`終端はKoushiと同じ設計言語**で、覚えることが少ない。
  ①連接が「無印の行」なのも良い(いちばん多い構造がいちばん短い)。
- **行頭記号(-/+/*)に意味を持たせる案**(+=フォーク・ジョインの「先」、*=定義)は面白い一方で、
  注意が1つ: Markdownの仕様では`-`と`+`と`*`は同じ「箇条書き記号」で、**レンダラによっては
  記号が変わると別のリストとして描画される**。PADレンダラは生テキストを読むので問題ないが、
  GitHubのプレビューとの二重運用を考えると、**意味は接頭トークン側に寄せ、行頭記号は
  自由(統一推奨)**とする方が安全かもしれない(例: 定義は`* 定義`でなく`- d. 名前`)。
  → 次のお茶の時間の論点に。
- 検討したい残り3点:
  1. **選択の条件式の書き場所**: `s. 条件式`(トークンの後=条件、子=分岐)で良さそう。
     分岐側のラベル(真/偽/case値)をどう書くか(`- y.`/`- n.`? 無印+慣習?)。
  2. **⑦Breakの飛び先**: 多重ループからの脱出は`b:2.`(2段抜け)のような段数指定か、
     ラベル指定か。
  3. **⑥定義の呼び出し側**: 定義済みブロックを呼ぶ記法(`-> 名前`? `call 名前`?)。
     PADの「定義(二重線の箱)」と「呼び出し」の対応をテキストでどう結ぶか
     (anchorの指紋と繋がると、コードとPADの照合=Okuteの取込に効く)。
- JIS X 0128は分冊されておらず高価(依頼者談・3万円)。記法はJISの図形の**意味**を
  Markdownへ写す方針であって、図形の再現ではない(規格の版権に配慮しつつ、意味論だけ倣う)。
