#### 1. koushi-dev(開発用リポジトリ)は要るか — 「不要」をおすすめします

結論: 作らなくて大丈夫です。理由は3つ。
1. **開発環境はもう在る**: Koushiの開発の場は宙の辻リポジトリ(tools/koushi.js+vscode-koushi/)で、`takeyosui15/koushi`は「リリースの器」です。つまり開発/本番の分離は、既に「宙の辻側=開発・koushi=公開」という形で成立しています(stagingで組んでから送る流れも、テスト済みのものしか外に出ない関所になっています)。
2. **利用者に届く瞬間は別にある**: 拡張の利用者に変更が届くのはリポジトリのpushではなく`vsce publish`の瞬間です。publishが「本番反映」の関所なので、リポジトリを2つに割る守りは重複になります。
3. **必要になったら枝で足りる**: 将来、外部の協力者が現れて作業が並ぶようになったら、koushiリポジトリ内のブランチ(main+開発ブランチ)で同じことができます。リポジトリを増やすのはその時でも遅くありません。
宙の辻で本番/開発を分けているのは「GitHub Pagesで常に公開されている本番」を守るためでした。koushiは「publishするまで何も公開されない」ので、同じ守りは要らない、という整理です。

#### 2. sample.mdをREADMEへ統合しました(ご提案の通り)

おっしゃる通りにしました。
- READMEの**英語License章の後・日本語章の前**に「Samples / サンプル」章を新設し、結合セル(アイコンの絵)・罫線つき状態遷移表・チェックリスト・input代表4種、の4例を英日の見出しで載せました。

- 一つだけ注意書きをサンプル章の頭に入れました: **GitHubのページ上ではkoushiフェンスは生のコードとして表示されます**(表として描かれるのは、拡張が入ったVSCodeのプレビューの中)。読者が「あれ、表にならない」と迷わないための一文です。

#### 3. 一式の送付 — コミットまで完了・pushで403(あと1クリックです)

`takeyosui15/koushi`の作成、確認しました(空っぽの作り方も手順書通りで完璧でした)。
一式をコピーして初回コミット(README・LICENSE・拡張・レンダラ・文法・テスト・icon=14ファイル)まで作ったのですが、**pushが403(権限なし)で弾かれました**。
原因ははっきりしています: ClaudeのGitHub Appが`soranotsuji-dev`にしかアクセス権を持っておらず、新しい`koushi`リポジトリには「読めるが書けない」状態です(公開リポジトリなので読むのは誰でもできる、の裏返しです)。
**お願い(1クリック+Save)**: GitHubの Settings → Applications → Installed GitHub Apps → Claude の「Configure」→ Repository access に `koushi` を追加してSaveしてください。
次のラウンドで「許可しました」と一言いただければ、即pushします(コミット内容はstagingから再現できるので、何も失われていません)。手順書(koushi-repo-guide.md)の手順2にもこの項を追記しました。

#### 4. 「うちのClaudeさん」と「よそのClaudeさん」のPRは区別できるか — できます

良い質問です。答えは「**PRの作者アカウントで確実に区別できます**」。
- 私(たけちゃんのClaude)がPRを出す時は、たけちゃんが許可したGitHub App(上の「Claude」)の名義で、**リポジトリ本体のブランチ**からPRが出ます。
- よそのClaudeさん(=他の誰かが使うClaude)は、その人のGitHubアカウントが作者になり、リポジトリ本体には書けないので**フォークからのPR**になります。
つまり見分け方は2重です: ①作者名(アプリ名義か・他人のアカウントか) ②出所(本体ブランチか・フォークか)。
コミット末尾の「Co-Authored-By: Claude」はどこのClaudeでも似た署名になりますが、あれは「AIが書いた」という印であって、身元はあくまで①②で判定します。なりすましの心配はいりません。
