### まず一言で:
- 可視マップは、**「この山(推し山)は、どこから見えるか」を地図に塗った、一度作ったら変わらない地図**です。
- 宙の辻の中で見るための機能で、計算は別に(まとめて)やっておき、アプリはその結果を読み込んで表示するだけです。

### 用語(このデッサンで使う言葉):
- **推し山**: 見たい山(目的点)。可視マップの対象は百名山・二百名山・三百名山・百高山の4つのリストにある山だけ
  (4つは重なる。合わせて約360の山頂。第143検品)。
- **タイル**: 地図を格子に切った1枚。地理院の標高タイル(z15)に揃える。北緯35〜36°でほぼ**1km四方**。
  緯度で伸び縮みする(北海道で約0.89km・沖縄で約1.09km)。1タイルは256×256画素、画素は約3.9m間隔。
- **見える/見えない**: 各画素に「地上1.5mに立った人」を置いた時、推し山の山頂が見えるかどうか。
- **島**: 「見える」画素が地図上でひとかたまりになった区域。可視マップはこの島を一覧にする。
- **静的資産**: 一度計算して配る成果物。ユーザーの入力で変わらない(推し山サイトの投稿とは別物)。
- **マーカー**: 可視マップが表示用に出す目印(山頂・全展望)。ユーザーが投稿する「ピン」(推し山サイト)とは別物。
- **山色**: 山ごとに割り当てる島の輪郭の色。表示天体のスタイル設定の16色を、選んだ順に使う。
- **全展望**: 選んだ山が全部見えること(その場所・その島)。
- **島の代表点**: 島の画素のうち、島の重心にいちばん近い画素の中心。必ず島の中にある(細長い島で重心が
  島の外へ出るのを防ぐ)。地図の移動先・都道府県の判定・項番の並びに使う。
- **生値**: 緯度経度を度の小数のまま(度分秒に直さず)表示すること(辻検索・辻メッシュのデッサンと同じ言葉)。
- **金色**: 見える場所の塗りの基準色(辻メッシュと同じ #FFD700)。

### 目的:
- 推し山が「どこから見えるか」の全体像(島)を、地図上で一望できるようにする。
- 辻メッシュ検索(重なる日時を探す)の前段として、「そもそも見える場所」を教える。
- 推し山サイト(動的・投稿型)の土台データになる(島の形と場所を渡す)。

### 概要:
- 機能概要(依頼者の構想・第136〜142)
  - 対象と範囲
    - 対象は**基本リスト(百名山・二百名山・三百名山)と百高山のみ**(第143: 依頼者が百高山を追加)。
    - 範囲は推し山を中心に**60km四方 / 100km四方 / 300km四方 / 700km四方**から選ぶ
      (700km四方=中心から±350km。富士山が紀伊半島の潮岬[約320km]から見えた実績に合わせた)。
  - 見える/見えないの判断(第139推奨案・依頼者承認)
    - 「見える」は、地形の丸み(地球の曲率)と大気差を入れた既存の可視判定で決める。
    - 遮るものは三段で見る: **地形**(地理院DEM)+**建物**(PLATEAUの実測高)+**樹冠**(木の高さ)。
    - 樹冠のデータは**Meta/WRIの1m樹冠高マップ**(CC-BY 4.0・認証不要・公開)を第一候補にする
      (第140に富士山域のタイルの実在を確認済み。クラウド最適化GeoTIFFなので必要な窓だけ読める)。
      控え: JAXA AW3D30(登録が要る)・ETH全球樹冠高10m(直接URLは未確認)。
    - 観測者は**地上1.5m**を標準にする(アプリの観測点高さの既定値1.5m化と揃える)。
    - 自分の立っている画素の木や建物は「遮るもの」に数えない(足元の木で自分が塞がれる誤判定を防ぐ)。
    - 樹冠の考慮は**オン/オフできる**(依頼者memo「植生の高さは、オプションで、ON OFFできる」)。
  - 計算の進め方(依頼者・第136)
    - 推し山を中心に**10km四方(=z15タイルの10×10のかたまり)に区切り、順番に計算**する。
      メモリを使い過ぎないための区切り方。
    - 全画素を見ずに、**見える可能性のある帯だけ**を先に絞る(候補帯プレフィルタ。辻メッシュで
      実証済みの方位角の索引の延長)。
    - この計算は**MCPで宙の辻を動かして**行う(MCPは計算の指揮者=順番出し・進み具合・中断と再開。
      言葉の決めごとはMCP対応のデッサンと一緒に確定)。
  - 結果の形(静的資産)
    - 一度計算した結果を**タイルごとの画像(見える=1/見えない=0)**として計算し、**配るのは島の輪郭
      (ベクトル)+島の索引(JSON)+計算条件のメモ(JSON)**にする案(第143検品の提案P1。採否待ち。
      タイル画像をそのまま配ると全山で数GB・数百万ファイルになる)。アプリはこれを読み込んで表示するだけ。
    - **ユーザーの入力は反映しない**(第138確定)。実地の見え方(木・天気)の答え合わせは推し山サイトの
      投稿(可視判定5パターンなど)が担う。
  - 島の一覧
    - 「見える」画素の**8近傍のつながり**を1つの島とする(案)。小さすぎる島を除く閾値は未決。
    - 島は**面積の大きい順**にリストにし、タップでその島へ地図が移動する。
    - **ピンは可視マップには置かない**(第142変更: ピンは推し山サイトで、ユーザーが写真から投稿する)。

#### 質問(依頼者の判断が要るもの):
- Q1 「:二百名山」「:三百名山」のチェックの意味: 200座・300座の全部か、百名山に加わる分だけか。
  (二百名山は百名山を全て含む。三百名山も百名山を全て含み、二百名山のうち荒沢岳1座だけが三百名山に無い。
  百・二百・三百の和集合は301座。百高山は約半分がどのリストにも無い脇峰で、4つの和集合は約358山頂)
  →AI案: 「200座全部・300座全部」。重なりは山リストに「所属」列(百/二百/三百/百高の印)を足せば一目で分かる。
- Q2 島リストの並び: 「面積の大きい順」(概要)と「北から南・東から西の項番」(詳細)は両立させてよいか。
  →AI案: 項番=代表点を北から南(同じなら東から西)に並べた固定の通し番号(並べ替えても変わらない名札)。
  初期の並びは面積の大きい順。行のタップで地図がその島へ移動、チェックで輪郭が点滅、と役割を分ける。
- Q3 山頂の目印: 「:山頂ピン」チェック(初期値オン)で黄色のマーカー、に一本化でよいか(今は105行目が無条件に読める)。
  色は黄色のままか、山色にするか(山色の4番目=黄と、塗りの金[#FFD700]と、黄色のマーカーが地図上で紛れる)。
  名前は「:山頂マーカー」「:全展望マーカー」と、投稿型の「ピン」と区別してよいか。
- Q4 全展望の目印: タイルごとではなく「全部見える島(縞の島)ごとに、代表点へ1本」でよいか
  (タイルごとに立てると数千〜数万本になる。縞のタイルと二重の表現にもなる)。初期値はオフでよいか。
