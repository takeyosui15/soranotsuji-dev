# anchor(錨) — 指紋のデッサン(第44ラウンド起草)

コード・文書の「この場所」を、行番号が腐っても・ファイルが引っ越しても指し続けられるようにする仕組み。
命名の心は「周りが変化しても、位置が変わらないもの」(依頼者)。
原案は第39〜41ラウンドの対話、パーマネントの本質の考察は第44ラウンドの依頼者メモから。

-------------------------------------------------------------------------------
## 原点(どんな問題があったから、これが欲しいか)
-------------------------------------------------------------------------------

- レビュー記録や学びから「コードのこの場所」を指したいが、**行番号は次の編集で腐る**。
  ファイルパスも移設(第43ラウンドのClaudeMederuU/移設のように)で変わる。
- リンク切れは「参照先が動いたのに、参照元が知らない」ことで起きる。
  欲しいのは、動いても追える錨。

-------------------------------------------------------------------------------
## 2つの指紋(第41ラウンドの整理)
-------------------------------------------------------------------------------

- **構造指紋 = 本人**(同一性)。
  プログラムを多分木(制御構造の木)で表し、ノード/ブランチ以下の部分木を正規化(空白・コメント除去)してハッシュを取る(Merkle木の要領)。
- **位置指紋 = 現住所**。
  ファイル+行内容+発行時刻から作る、人間とツールがジャンプするための住所。引っ越したら更新される方が正しい情報。
- 「引っ越しても本人は本人」。錨の本体は構造指紋に置く。

### 構造指紋が「変更に強い」理由(第44ラウンドの依頼者考察)

- 部分木のハッシュは、**内包しない部分木が変更されても変わらない**。
  位置指紋(ファイル全体が変わると変わる)より変更に強い。
- さらに、**ハッシュの更新の伝播が「変更の影響範囲」を教えてくれる**:
  子のハッシュが変わると親のハッシュも変わる(Merkleの性質)ので、根から変更ノードへの経路=変更の波及線。
  実行順序が木の辿り順と対応する言語なら、変更ノードまでの経路が「ここから先が影響を受けうる」の目安になる。

-------------------------------------------------------------------------------
## パーマネントの本質(第44ラウンドの依頼者考察を設計原則に)
-------------------------------------------------------------------------------

- 指紋そのものは、内容が変われば書き換わる。**指紋は永続ではない**。
- パーマネントにするのは指紋ではなく、**「このハッシュは、どのハッシュに書き変わりましたか」に答えられる仕組み**の方。
  問い合わせに答えが返るなら、指紋が変わっても追える=**リンクは実質パーマネントになる**。
- つまり anchor の本体は「指紋の発行」と「**指紋の系譜(書き換わりの履歴)**」の2つ。

### 履歴の担い手(3案の比較と採用案)

1. 参照元・参照先の両方を毎回更新する
   * リンク切れは消えるが、参照元が散らばるほど更新が漏れる(人は忘れる)。
2. ドキュメント自身が自分のハッシュ履歴を持つ
   * 他のドキュメントの負担は減るが、履歴が各所に分散する。
3. リポジトリが履歴を担う(問い合わせるとリポジトリが答える)
   * 正が1つ(MederuUのハブ思想と同じ)。
- **採用案 = 3を基本に、2を台帳で実装する折衷**:
  リポジトリに**追記型の台帳 `anchors.jsonl`**(1行=1つの書き換わりイベント: 旧指紋→新指紋・日時・コミット・理由)を置く。
  台帳は「1ファイル=履歴の正」(ドキュメントが持つ)でありつつ、リポジトリにあるので「リポジトリに問い合わせる」も満たす。
  追記型なので過去は書き換わらない(発行済みURL辞書の凍結・学びは重ねる、と同じ原則)。

### gitとの関係(車輪を再発明しない)

- 実は**gitが既にMerkle木のハッシュ履歴データベース**(コミット=断面のスナップショット、親リンク=系譜)。
  `git log -S`(内容検索)や`git log -L`(行範囲の追跡)で「内容の引っ越し」もある程度追える。
- anchorが足すのは**意味の層**: gitのハッシュは「ファイル・ツリー単位」だが、anchorは「制御構造の部分木単位」。
  「この関数のこのループ」に錨を打てるのはanchorだけ。gitは土台として使い、台帳のイベントにコミットIDを添えて両者を結ぶ。

## ビューワー(第44ラウンドの質問「どんなスライスがあれば良いか」への設計)
-------------------------------------------------------------------------------

データ構造は**指紋の系譜DAG**(ノード=指紋、エッジ=書き換わりイベント)。これを3つの軸でスライスする:

1. **空間スライス(いまの木)**: あるコミット断面での、制御構造の木+各ノードの指紋。
   「どこに錨があるか」のツリービュー(=PADの木と同じ形! レンダラを共有できる)。
2. **時間スライス(1本の系譜)**: 1つの錨の「いつ、何に書き換わったか」の年表。
   各イベントに日時・コミット・(あれば)理由。**OKFのlog.md(変更の時系列履歴)と同じ思想**。
3. **差分スライス(変更の波及)**: 2つの断面の間で指紋が変わったノードだけを、根からの経路で表示。
   =「この変更の影響範囲」ビュー(依頼者考察の可視化)。

- 「リポジトリは断面しか持たないので、一つ前の指紋の履歴を持てば追跡できるか」への答え:
  **はい。各イベントが「旧指紋→新指紋」の1ホップを持てば、断面の列が鎖に変わります**(単方向リンクリストと同じ。gitのコミット親リンクと同型)。
  台帳が1ホップずつ記録し、ビューワーが鎖を辿って系譜を復元する、が役割分担。

## PADとの接続(`d:#指紋.` の2本立ての意味の提案)
-------------------------------------------------------------------------------

- PADデッサン02の `pad:#a1b2c3d4-#A1B2C3D4.` の2本は、**構造指紋-位置指紋**の対と解釈するのを提案
  (前=本人・後=現住所。次のお茶で擦り合わせ)。
- 呼び出し側 `- d:#構造指紋. 名前` は本人だけを指す(引っ越しに強い参照)。
  ビューワーはそこから台帳を引いて現住所へジャンプする。

## スモールスタート(実装順)
-------------------------------------------------------------------------------

1. `anchor.js`(tools/): 波括弧の入れ子木+正規化テキストのハッシュ(第41ラウンド合意の最小版)。
   - 発行: ファイルを読み、指定ノードの構造指紋+位置指紋を印字
   - 検証: 錨の一覧を読み、現ファイルで指紋を再計算して「不変/書き換わり」を判定
   - 検出: 同一指紋の部分木の列挙(=重複コード検出。リファクタリングBの道具と一石二鳥)
2. 台帳 `anchors.jsonl` の追記(書き換わり検出時に旧→新のイベントを書く)
3. ビューワー(空間→時間→差分の順。PADレンダラと骨格共有)
