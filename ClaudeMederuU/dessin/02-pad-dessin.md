# PAD — Markdown-PAD記法の起草メモ(第42ラウンド)

PAD(Problem Analysis Diagram・JIS X 0128)をMarkdownの箇条書きで書く記法の、依頼者原案の
捕獲と検討メモ。本格的なデッサンは進め方③(PAD/Okute)の番で行うが、
「頭の中のデッサンが新鮮なうちに文書へ」の原則で先に記録する。

-------------------------------------------------------------------------------
## 依頼者原案(第42ラウンド): 7つの構造で足りる
-------------------------------------------------------------------------------

「①連接②選択③反復④フォーク⑤ジョイン⑥定義(関数呼び出し)⑦Breakが揃っていれば大丈夫」

```markdown
- 連接1
- 連接2
- 連接3
```

```markdown
- s. 選択1
  - 選択肢1
  - 選択肢2
```

```markdown
- w. 繰り返し前判定
  - 連接
```

```markdown
- l. 繰り返し後判定
  - 連接
```

```markdown
+ f. フォーク元
  - f. フォーク先1
  - f. フォーク先2
```

```markdown
- j. ジョイン元1
- j. ジョイン元2
  + j. ジョイン先
```

```markdown
* 定義
```

```markdown
- b. Break
```

- フォーク/ジョインは最新のPAD系規格の拡張(並行処理の表現)に倣う(依頼者)。
- 実例第1号: MederuU器デッサンの「中心ワークフロー」図をこの記法で書き直した
  (`00-dessin.md`参照。ASCII罫線の図はインデント崩れするため全廃)。

## AIの所感(第42ラウンド)
-------------------------------------------------------------------------------

- **接頭トークン(s./w./l./f./j./b.)+`.`終端はKoushiと同じ設計言語**で、覚えることが少ない。
  ①連接が「無印の行」なのも良い(いちばん多い構造がいちばん短い)。
- **行頭記号(-/+/*)に意味を持たせる案**(+=フォーク・ジョインの「先」、*=定義)は面白い一方で、
  注意が1つ: Markdownの仕様では`-`と`+`と`*`は同じ「箇条書き記号」で、**レンダラによっては
  記号が変わると別のリストとして描画される**。PADレンダラは生テキストを読むので問題ないが、
  GitHubのプレビューとの二重運用を考えると、**意味は接頭トークン側に寄せ、行頭記号は
  自由(統一推奨)**とする方が安全かもしれない(例: 定義は`* 定義`でなく`- d. 名前`)。
  → 次のお茶の時間の論点に。
- 検討したい残り3点:
  1. **選択の条件式の書き場所**: `s. 条件式`(トークンの後=条件、子=分岐)で良さそう。
     分岐側のラベル(真/偽/case値)をどう書くか(`- y.`/`- n.`? 無印+慣習?)。
  2. **⑦Breakの飛び先**: 多重ループからの脱出は`b:2.`(2段抜け)のような段数指定か、
     ラベル指定か。
  3. **⑥定義の呼び出し側**: 定義済みブロックを呼ぶ記法(`-> 名前`? `call 名前`?)。
     PADの「定義(二重線の箱)」と「呼び出し」の対応をテキストでどう結ぶか
     (anchorの指紋と繋がると、コードとPADの照合=Okuteの取込に効く)。
- JIS X 0128は分冊されておらず高価(依頼者談・3万円)。記法はJISの図形の**意味**を
  Markdownへ写す方針であって、図形の再現ではない(規格の版権に配慮しつつ、意味論だけ倣う)。

## 第43ラウンドの詰め(依頼者回答+AIの意見)
-------------------------------------------------------------------------------

### 決まったこと・方向が出たこと

- **定義は`- d. 定義名`**(行頭記号`*`をやめてトークンへ。Markdown仕様との衝突回避)。
- **反復の子は「連接」**(選択肢ではない。依頼者修正済み)。
- **Break+ラベル**: `- b:2. #ラベル名`(段数とラベルの両方を書ける)+⑧ラベル定義 `- lb:#ラベル名.`
- **選択の分岐ラベル**(依頼者案・採用方向):

```markdown
- s. 条件
  - s:y.
    - 連接
  - s:n.
    - 連接
  - s:"文字列など何でも".
    - 連接
```

- **呼び出しと定義の対応**(依頼者案・採用方向): 呼び出し側 `- d:#指紋. 定義名`、定義側は

```markdown
- pad:#a1b2c3d4-#A1B2C3D4.
  - pad:name. 定義名
  - pad:synopsis. 使い方
  - pad:description. 説明
  - pad:history. 生まれた経緯
  - pad:seeAlso. 関連
```

  の5セクション(=man由来の章立てと同じ。ツールヘッダ・legendsとも統一)。

### フォーク/ジョインの記号 — **確定(第44ラウンド・依頼者採用)**

対称形の`f+./f-./j-./j+.`で確定(「+=1対Nの1側(束ねる点)、-=N側」の1規則):

```markdown
- f+. フォーク元
  - f-. フォーク先1
  - f-. フォーク先2
```
```markdown
- j-. ジョイン元1
- j-. ジョイン元2
  - j+. ジョイン先
```

- 理由: ①意味が全てトークン側にあり行頭記号は自由(Markdown仕様と衝突しない)
  ②「+=1対Nの1側(束ねる点)、-=N側」という1つの規則で両方読める
  ③`f+.`と`f.`の混在型(片側だけ無印)より、対で揃っている方が検索(grep)しやすい。

### 部品の充足(「これで足りているか」への評価)

- 構造は**9部品**: ①連接(無印) ②選択`s.` ③前判定反復`w.` ④後判定反復`l.`
  ⑤フォーク`f+./f-.` ⑥ジョイン`j-./j+.` ⑦定義`d.`(+呼び出し`d:#指紋.`) ⑧Break`b.`/`b:N. #ラベル`
  ⑨ラベル`lb:#ラベル名.`
- 理論上は連接・選択・反復で計算完備(構造化定理)なので、**制御の「構造」としてはこれで完備**。
  return/throw(例外)は「構造」ではなく「文」なので、連接の言葉として書けば足りる
  (例: `- return 値` / `- throw エラー`)。部品を増やさないのが依頼者の7±2の美学に合う。
- `"`括りの構文解析: **難しくない**。トークンは「`:`から`.`まで」、`"`が来たら次の`"`まで読む、
  エスケープは`\"`の1規則だけ決めれば良い(JSONと同じ)。採用に賛成。
- **Koushiとの接頭トークン被り検査(PAD内に表を書く時のため)**: PAD側 s/w/l/f+/f-/j+/j-/d/b/lb/pad と
  Koushi側 t/r/c+input22種(btn/chb/clr/dat/dtl/eml/fil/hdn/img/mnt/nmb/pwd/rad/rng/rst/src/smt/tel/txt/tim/url/wek)は
  **現時点で衝突なし**(単文字組t,r,cとs,w,l,f,j,d,bは別・3文字組にpadとlbは不在)。
  今後の追加時は「PADは1〜2文字+記号、Koushiのinputは3文字」を守れば構造的に被らない。
